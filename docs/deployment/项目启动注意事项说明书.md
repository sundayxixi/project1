> 适用项目：辰光 Agent 平台（FastAPI + React）

> 验证环境：Windows 11（10.0.26300）+ Python 3.14.8 + Node.js v24.22.0 + npm 11.19.1

## 1. 启动方式

### 1.1 一键启动（推荐）

在项目根目录双击 `start.bat`，或在命令行执行：

```bat
start.bat
```

无人值守（自动化脚本、CI）场景请使用：

```bat
start.bat --no-pause
```

`--no-pause` 会让脚本在成功或失败后直接退出，不会停在“请按任意键继续”。双击运行时仍保留该暂停，方便查看输出。

脚本会自动完成以下 6 个步骤：

| 步骤 | 内容 | 说明 |
|------|------|------|
| 0/6 | 基础文件检查 | 检查 `requirements.txt`、`app/package.json`；首次运行时由 `.env.example` 生成 `.env`，并生成 `app/.env.local`（前端连接真实后端）；`app/.env.local` 已存在但 `VITE_USE_MOCK` 不是 `false` 时给出警告 |
| 1/6 | Python 环境 | 检测 Python ≥ 3.10；校验 `.venv` 解释器是否真的可用，失效时自动备份并重建 |
| 2/6 | 后端依赖 | 检查 fastapi、uvicorn、aiosqlite、fakeredis、alembic、sqlalchemy、minio、redis、loguru、PIL、jwt 等是否可导入，缺失则自动 `pip install` |
| 3/6 | 数据库 | 调用 `bootstrap_db.py` 建库/迁移/灌入演示数据 |
| 4/6 | 前端依赖 | 检查 npm 是否可用，`app/node_modules` 缺失时自动 `npm install` |
| 5/6 | 启动服务 | 端口空闲时分别在新窗口启动后端 8080、前端 5173；端口已被占用时先做健康检查，确认是本项目服务才跳过，否则告警 |
| 6/6 | 等待就绪 | 并行轮询 `/health` 与前端首页，就绪后自动打开浏览器 |

启动成功后会输出：

```text
后端 API 文档: http://localhost:8080/docs
健康检查:      http://localhost:8080/health
前端界面:      http://localhost:5173
默认账号:      admin / 123456
```

> 服务分别运行在两个新打开的命令行窗口中。**停止服务 = 关闭对应窗口**，或按下方第 7 节通过 PID 结束进程。

### 1.2 手动启动（排查问题时使用）

需要打开两个终端。

**终端一：后端**

```bat
cd /d D:\rengongzhineng
.venv\Scripts\activate
python bootstrap_db.py
python -m uvicorn src.main:app --host 127.0.0.1 --port 8080
```

**终端二：前端**

```bat
cd /d D:\rengongzhineng\app
npm run dev -- --strictPort
```

## 4. 关键配置说明

### 4.1 数据库：SQLite（无需 Docker）

`src/core/config.py` 中 `DATABASE_URL` 当前固定返回：

```python
"sqlite+aiosqlite:///./chenguang.db"
```

因此 `.env` 中的 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASSWORD`、`DB_NAME` **当前不会生效**。这是本地免 Docker 开发模式，不是生产配置。

`bootstrap_db.py` 的自动处理逻辑：

1. 数据库文件不存在 → 调用 `init_data.py` 建表、灌入演示数据，并 `alembic stamp head`；
2. 文件存在但缺少 `alembic_version` 表 → 按是否有业务数据决定重建或直接标记为最新；
3. 版本落后 → 执行 `alembic upgrade head`；
4. 迁移失败（脏状态）→ 旧库备份为 `chenguang.db.bak_时间戳` 后重建。

> SQLite 适合本地开发。多人同时写入或需要高并发时，请切换到 MySQL（见第 10 节）。

### 4.2 缓存：fakeredis（无需 Redis）

`src/infra/redis_cache.py` 使用进程内 `fakeredis`，接口与真实 Redis 完全一致。影响：

- 验证码保存在后端进程内存中，**后端一重启，旧验证码全部失效**，重新获取即可；
- 多进程/多实例部署时各自内存不共享，本地开发不受影响。

### 4.3 MinIO：默认未启动

`.env` 中 MinIO 指向 `127.0.0.1:9000`，但 `start.bat` 不会启动 MinIO。后端启动时 `ensure_bucket_exists()` 连接失败会打印：

```text
minio 桶创建失败，文件上传功能将无法使用：... [WinError 10061] ...
```

这是**预期告警，不会导致启动失败**，但知识库文件上传功能不可用。该连接重试会让后端启动多花约 10～20 秒。

需要文件上传时二选一：

- 启动 Docker 基础设施：`docker compose -f docker/docker-compose.yaml up -d`；
- 或后续接入项目内已有的内存模拟实现 `src/infra/mock_minio.py`（目前尚未在 `minio_client.py` 中启用）。

### 4.4 前端 mock 开关

前端通过 `app/.env.local` 控制：

```ini
VITE_USE_MOCK=false
VITE_API_BASE=http://localhost:8080/api/v1
```

- `app/.env.local` 被 `app/.gitignore` 中的 `*.local` 忽略，**不会提交到仓库**；
- 如果缺少该文件，`src/services/config.ts` 默认 `VITE_USE_MOCK !== 'false'` 为真，页面会使用 mock 数据，看起来“启动成功但数据不对”；
- `start.bat` 已自动在缺失时创建该文件。若要体验纯前端 mock，把它改为 `VITE_USE_MOCK=true` 后重启 Vite。

### 4.5 端口

| 服务 | 端口 | 说明 |
|------|------|------|
| 后端 | 8080 | `--host 127.0.0.1` |
| 前端 | 5173 | Vite + `--strictPort`，端口被占用时直接失败而不是漂移到 5174 |

`start.bat` 在启动前会检测端口：端口被占用时，会再用健康检查确认该端口上运行的是不是本项目服务。

- 是本项目服务（`/health` 返回正常、前端首页可访问）→ 跳过启动，直接复用；
- 被其他程序占用 → 打印警告并跳过该服务，不会误报“启动成功”。

> 因此看到“端口 … 被其他程序占用”时，必须自行释放端口，否则第 6 步会超时。

## 5. 本次启动修复内容（2026-10-25）

1. **重建失效虚拟环境**：原 `.venv` 由另一台电脑的 `C:\Users\admin\...\Python313` 创建，`python.exe` 报 `did not find executable`。已用本机 Python 3.14.8 重建，并删除 135 MB 的旧环境。
2. **修复 `requirements.txt` 编码**：原文件为 UTF-16 LE（带 BOM），在 git 中被识别为二进制。已转为 UTF-8，便于 diff 与 pip 读取。
3. **移除 `asyncmy`**：该 MySQL 驱动在 Python 3.14 下无预编译 wheel，需要本地编译 MySQL C 客户端；当前项目使用 SQLite，已从依赖中移除。
4. **补充 `minio==7.2.20`**：`src/infra/minio_client.py` 直接 `import minio`，但原依赖清单缺失该项，会导致后端导入失败。
5. **`start.bat` 增强**：
   - 校验 Python 版本 ≥ 3.10，并跳过 Windows 商店占位符；
   - 校验 `.venv` 解释器能否真正运行，失效时自动重命名备份为 `.venv.broken_随机数` 并重建；
   - 依赖检查扩展到 minio、redis、loguru、PIL、jwt、pydantic_settings，安装后二次校验；
   - 检查 npm 是否存在；
   - 首次运行自动生成 `.env` 与 `app/.env.local`；
   - 前端使用 `--strictPort`，避免端口漂移后等待逻辑误判；
   - 启动提示中明确说明 MinIO 告警属正常现象。
6. **`wait_ready.py` 改为并行轮询**：原实现用 `all()` 串行等待，后端失败时不会检查前端，且最坏等待时间为 2 倍超时；现在共享同一个总超时。
7. **`start.bat` 支持无人值守**：新增 `--no-pause` 参数。此前脚本末尾的 `pause` 会让自动化调用一直挂起；现在 `start.bat --no-pause` 会在完成或失败后直接退出，双击运行时行为不变。
8. **端口占用判定更严格**：端口被占用时不再直接假设“服务已在运行”，而是用 `%PY%` 请求对应健康检查地址；只有确认是本项目服务才跳过，否则明确告警（见 4.5）。避免“端口被其他程序占用但脚本报告启动成功”的假象。
9. **前端 mock 配置校验**：`app/.env.local` 已存在但 `VITE_USE_MOCK` 不是 `false` 时打印警告，避免页面显示 mock 数据却被误判为后端异常。
10. **验证结果（2026-10-25 修改后复测）**：
    - 完整冷启动（先结束旧进程再运行脚本）通过，后端约 10 秒内就绪；
    - 二次运行（服务已在运行）正确识别并跳过两个服务；
    - `/health` 返回 `{"status":"ok"}`，`/docs`、验证码接口、用户分页接口均返回 200；
    - 前端 `http://localhost:5173` 返回 200，Vite 正常加载。

## 6. 常见问题排查

### Q1：双击 `start.bat` 后提示 `.venv` 不可用 / `did not find executable`

原因：`.venv` 是从其他电脑或用户目录拷贝来的，`pyvenv.cfg` 中的 `home` 指向不存在的解释器。

处理：新版 `start.bat` 会自动把旧的 `.venv` 改名为 `.venv.broken_随机数` 并重建。也可以手动执行：

```bat
rmdir /s /q .venv
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

备份目录确认无用后可直接删除。

### Q2：`pip install asyncmy` 编译失败

报错类似 `Failed building wheel for asyncmy`、`Microsoft Visual C++ 14.0 required`。

原因：`asyncmy` 在 Python 3.14 没有预编译 wheel，且当前项目已改用 SQLite，不需要它。

处理：确认 `requirements.txt` 中**没有** `asyncmy`。若将来切回 MySQL，建议使用 Python 3.13，并安装 MySQL 开发库与 C++ 编译工具。

### Q3：`requirements.txt` 出现乱码或被 git 当成二进制

原因：文件被保存成了 UTF-16（Windows 记事本“Unicode”编码）。

处理：必须保存为 **UTF-8（无 BOM）**。可用 VS Code 右下角编码切换为 “UTF-8” 后保存。

### Q4：pip 安装慢或超时

```bat
pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

然后重新运行 `start.bat`。npm 慢时可执行：

```bat
npm config set registry https://registry.npmmirror.com
```

### Q5：端口 8080 / 5173 被占用

查看占用进程：

```bat
netstat -ano | findstr :8080
netstat -ano | findstr :5173
```

结束进程：

```bat
taskkill /PID <上一步的PID> /F
```

### Q6：前端页面能打开，但接口全部失败 / 控制台报 CORS

- 确认访问的是 `http://localhost:5173`，不要用 `127.0.0.1`；
- 确认后端 8080 正在运行：`curl http://127.0.0.1:8080/health`；
- 确认 `app/.env.local` 中 `VITE_USE_MOCK=false`、`VITE_API_BASE=http://localhost:8080/api/v1`，改完需重启 Vite。

### Q7：页面显示的是假数据（mock）

说明 `VITE_USE_MOCK` 未生效为 `false`。检查 `app/.env.local` 是否存在、是否拼写正确，并重启前端进程。

### Q8：登录提示“验证码不存在或已过期” / “验证码错误”

- 验证码有效期 5 分钟，过期后重新点击图片获取；
- 后端重启会清空 fakeredis 中的所有验证码；
- 若持续失败，确认后端控制台没有 Redis 相关异常。

### Q9：启动日志出现 MinIO 连接失败

预期行为，见 4.3。不影响登录、列表、Agent 管理等主流程，仅影响知识库文件上传。

### Q10：数据库结构乱了，想重新初始化

先关闭后端窗口，然后：

```bat
ren chenguang.db chenguang.db.old
.venv\Scripts\python.exe bootstrap_db.py
```

`bootstrap_db.py` 会自动建表并灌入演示数据。旧库可保留或删除。

### Q11：`python` 命令打开微软商店或版本过低

`start.bat` 会实际执行版本检查，失败后自动尝试 `py -3`。若仍失败，请安装 Python 3.10+ 并勾选 “Add Python to PATH”，不要依赖 Windows 商店别名。

### Q12：`npm` 不是内部或外部命令

安装 Node.js 18+（建议 LTS），安装后重开命令行，确认 `node -v`、`npm -v` 均可输出。

## 8. 文件编码注意事项（重要）

`start.bat` 使用 **GBK 编码**，并配套：

```bat
chcp 936
set "PYTHONIOENCODING=gbk"
```

编辑 `start.bat` 时必须保持 GBK，否则中文提示会乱码。VS Code 保存时请选择 “GBK” 编码；如果改成 UTF-8，需要同时把 `chcp 936` 改为 `chcp 65001`，并把 `PYTHONIOENCODING` 改为 `utf-8`，两者必须成对修改。

其他文件编码约定：

| 文件 | 编码 |
|------|------|
| `start.bat` | GBK（CRLF） |
| `requirements.txt` | UTF-8（LF，无 BOM） |
| Python / TypeScript / Markdown | UTF-8 |
| `.env`、`.env.example` | UTF-8 |

## 9. 切换到真实 MySQL / Redis / MinIO（备忘）

当前启动链路全部为本地免 Docker 模式。如需切回真实服务：

1. **MySQL**：修改 `src/core/config.py` 的 `DATABASE_URL` 为 `mysql+asyncmy://...`，在 `requirements.txt` 恢复 `asyncmy`（建议 Python 3.13），并配置 `.env` 中 `DB_*`；
2. **Redis**：把 `src/infra/redis_cache.py` 改回 `redis.Redis(connection_pool=...)`，并配置 `.env` 中 `REDIS_*`；
3. **MinIO**：启动 `docker compose -f docker/docker-compose.yaml up -d`，确保 `.env` 中 `MINIO_ENDPOINT/ACCESS_KEY/SECRET_KEY/BUCKET` 与服务端一致；
4. 执行 `alembic upgrade head`，再重启后端。

> `docker/docker-compose.yaml` 中的 MinIO 镜像近期被改为 `elestio/minio:latest`，使用前请确认镜像可正常拉取。
